# FLASH-GEMM vs OpenBLAS Haswell — изучение исходника и перенос

Изучено (GitHub, OpenMathLib/OpenBLAS): `kernel/x86_64/sgemm_kernel_8x4_haswell_2.c`,
`driver/level3/level3.c` (Goto-драйвер), `param.h` (HASWELL: P=320, Q=320, UNROLL_M=8,
UNROLL_N=4). Сверено с нашим `src/atom/flash/flash_gemm.rs` + `jit.rs`.

## 1. Ядро: что совпадает

| | OpenBLAS Haswell | AtomNET FLASH |
|---|---|---|
| Тайл | m16n6 / m8n12 (12 YMM-аккумуляторов) | 6×16 (12 YMM, без спилов) |
| k-unroll | ×2 (k2) | ×8 (глубже конвейеризация L2-латентности) |
| A | interleaved `[k][8]` + `vmovups`/`vmovsldup`/`vmovshdup` | scattered (6 broadcast) или interleaved (`ATOMNET_GEMM_PACKA=1`, 32 B/шаг) |
| B | `[k][n]` панели, `vbroadcastsd` | `[kk][n]` панели, 2 `vmovups`/шаг |
| Эпилог | shuffle-save (`vunpckl/h`) + `vfmadd213` (alpha, beta) | прямой store (beta=0) + fused bias+SiLU |
| L1/L2 | Goto `JC → LS → IS` | `jc → pc` по панелям, `j` снаружи / `i` внутри (BLIS) |
| Потоки | 2D `divide_rule` (M × N) | 2D-сетка div_m × div_n (только для широких C) |

Вывод: ядра эквивалентны (один и тот же регистровый класс, тот же FMA/лоад-профиль
~0.67 против ~0.67). A-pack у OpenBLAS — постоянная часть (1–2 кэш-линии A/шаг
против наших 6 при scattered) — но при L2-резидентных A (≤512³) разница
нейтральна (измерено: PACKA on/off — паритет); при DRAM-масштабах выигрыш
съедается стоимостью упаковки (измерено на 4096³: нейтрально/хуже).

## 2. Замеры (чистый процесс, без numpy в том же процессе, `taskset 0-5`)

> ⚠️ Агентский ловушка: OpenBLAS-воркеры спинятся и мешают обычным
> in-process сравнениям (наш первый замер 5.7 мс → в чистом процессе 1.59 мс).
> Честно — только раздельные процессы.

| GEMM | NumPy (OpenBLAS) | AtomNET | Отставание |
|---|---|---|---|
| 512³ | 1.39 мс | 1.59 мс | −12% (169 vs 193 GFLOPS, 59% пика) |
| 1024³ | 11.3 мс | 13.7 мс | −21% |
| 2048³ | 88.4 мс | 112.7 мс | −27% |
| 256×2048×8192 (wide) | 47.0 мс | 68.1 мс | −45% |

Пробовано через env (нейтрально): `ATOMNET_GEMM_MC 96→320`, `KC 128→256/320`,
`NC 256→512`, `ATOMNET_GEMM_PACKA`.

## 3. Что перенесено

- **2D-сетка потоков `div_m × div_n`** (`gemm_grid`, `gemm_fork_job`): N-split
  только при `cols > rows` (широкое C — типично LLM FFN/QKV): каждый воркер
  читает 1/div_n часть B вместо всей B. На квадратных — чистый M-split
  (N-split там даёт дисбаланс jc-панелей и пустые воркеры — измерено −30%).
  Бит-в-бит паритет 1 vs N потоков (тест `gemm_blocked_2d_grid_matches_sequential`,
  плюс fused `gemm_silu`).
- Подтверждено: `matmul_np` zero-copy, `matmul` на блочном ядре.

## 4. Вычислительная система: NPU-эмулятор + AOT/JIT + zero-copy

- **Виртуальный ISA** (`src/atom/isa.rs`): единый гейт AVX2/FMA — каждое
  виртуальное ядро видит регистровый файл (16 YMM, 2 FMA-порта, tier);
  все JIT/SIMD-гейты идут через него, `ATOMNET_ISA_TIER=scalar` форсирует
  фолбэк для тестов. Статус: `atomnet.virtual_isa()`.
- **NPU-эмулятор** (`src/atom/npu/`): виртуальный mac-массив (кластеры 6×16)
  распределён по CPU-потокам; детерминирован (1 поток = N бит-в-бит);
  профиль `ATOMNET_NPU_PROFILE=tiny|standard|turbo`; статус через
  `atomnet.npu_status()`, распределение — `atomnet.npu_distribute()`.
  Виртуальных ядер может быть больше потоков: `ATOMNET_NPU_CORES=32` —
  32 зоны на одном потоке (эмуляция большого NPU; скорость при этом —
  скорость потока, результаты те же). Глубокий режим:
  `ATOMNET_THREADS=1 ATOMNET_NPU_PROFILE=deep` (32 виртуальных ядра,
  бенч `benchmarks/bench_deep1.py`: MLP-epoch 31 мс, GEMM 512³ 4.6 мс).
  `atomnet.npu_cycles(flops)` — моделируемые циклы реального NPU.
  Честно: 1 поток в 2.7–3× медленнее 6 потоков (физика, не баг) — виртуальные
  ядра дают модель параллели, а не бесплатную скорость.
- **AOT v2/ JIT единым штабом**: `ATOMNET_AOT_PATH`, `atomnet.jit_source()`.
  Caller-side оверхед вычищен: `CpuNpu::matmul` без копий в Tensor,
  NPU-Python `_np`-пути с прямым выходом в numpy, AtomArray без клонов
  операндов (borrow), единый `gemm_auto_parts` порог.
- Замерено (512³): `npu_matmul_np` 0.96 мс = `gemm_blocked_np` 0.98 мс,
  паритет 0.0; strided-входы обрабатываются (F-order → C-копия).

## 5. AOT v2: полный дамп DynASM-ядер (`ATOMNET_AOT_PATH`)

Один файл `ATOMJIT2` — все 23 ядра (GEMM ×8, math, elem ×8, Q4, atomjit):
при повторных коротких процессах вместо сборки DynASM ядра маппятся
(патчинг абсолютных адресов MathTable при импорте, CPU-гейт AVX2+FMA,
фолбэк на сборку при несовпадении).

```python
atomnet.aot_dump("/path/kernels.aot")   # один раз (на этой машине)
# затем в процессах:
# ATOMNET_AOT_PATH=/path/kernels.aot python train.py
atomnet.jit_source()  # "assembled" | "aot" | "none"
atomnet.aot_check(path)  # проверка файла без установки
```

Замер: первый GEMM 3.53 мс (AOT) против 3.78 мс (сборка) — выигрыш
мал, т.к. cold start доминируется fork-пулом и page faults; AOT полезен
не секундами, а гарантиями (ноль DynASM в проде, отлаженный код, проверка
прибивость) и для short-lived скриптов. Полный бинарный деплой модели —
следующий слой поверх (FlashArchive-манифест + бандл, см. roadmap).

## 6. Регистровые регионы: регионы → кластеры

Систематизировано (и измерено):

- **Регион** — блок MC×NC (`GemmRegion {r0, r1, jc0, jc1}`), C-регион живёт
  в L2 все k-панели; границы выровнены на 6 строк и NC-панели.
- **Регистровый кластер** — JIT-тайл 6×16 (12 YMM, `RegisterCluster`),
  элементарная единица исполнения; аккумуляторы живут в регистрах
  ровно один k-панельный вызов.
- **Очередь регионов**: воркеры тянут регионы по атомарному счётчику
  (ворк-стилинг в родном fork-пуле, `next_region`). Детерминированность
  сохранена: регион = независимая зона C.
- **Переразбиение** `ATOMNET_GEMM_OVER` (по умолчанию 2): регионов в 2×
  больше воркеров. Измерено: OVER=2≈3≈4 быстрее OVER=1 на 5–8% на
  всех формах (square/ragged/wide), OVER=1 — статичная разбивка.
  Бит-в-бит паритет 1 vs N потоков на всех shapes (включая fused SiLU).

## 7. DSR-регионы: помогает или нет (прототип)

Идея: переписать настройку на распределительную систему регионов (каждая
регион-фрагмент считает только своё + мёртвые регионы пропускаются).

Что уже было: `FlashArena` hot/cold (чанки по 256 строк, RegionManager с
RAM-бюджетом) + 2D-сетка выше. Новое: `gemm_blocked_masked_into` —
битмаска `row_alive` живых строк; мёртвые 6-строчные группы пропускают
ядро (в C — нули). Контракт — вызывающий гейтит мёртвые строки в 0
(`QairoLivingLayer::forward_gated`).

Замеры (2048×1024×1024, 6 потоков, clean): dense 26.0 мс → 50% мёртвых
строк 13.1 мс (**~2×**, пропорционально доле скипа); dense-маска —
полный паритет 0.0. «Географические» регионы (NUMA/CCX) на этой машине
(1 нода, 1 L3) не дадут ничего; на multi-CCX помогжет сочетание с CM-порядком
`l3_clusters`.

Вердикт: полный рерайт настройки на DSR не нужен — регионы уже встроены
(маска + 2D-сетка + RegionManager). Выигрыш есть только там, где регионы
различаются (sparse/live-слои); на dense GEMM — neutral.

## 8. Что осталось (честный список)

- ~20–45% на больших/wide GEMM — это DRAM-трафик B и C-аккумуляция по k-панелям.
  Следующий рычаг — L2-бюджет драйвера (P адаптируется по `l2size`, как в
  `level3.c`) и perf-счётчики (`perf stat`: L1/L2 misses, FMA stall), иначе
  вслепую не выбить. Отдельно: pack B (64 МБ запись/чтение) на wide — кандидат
  на reuse упакованной B между вызовами с тем же указателем.
- Наших фирменных плюсов у OpenBLAS нет: fused GEMM+SiLU (один проход),
  int4 `FlashCompressed`, zero-copy в numpy-массив, XOR-физика.
